# AI side, Fall weeks 4 and 5: setup, decisions, findings

Date: 2026-11-02 (start of week 6). Author: Devin, with Claude Code.
Covers the two proposal items that were due before this week:

- Week 4: install ST's AI tools and run ST's ready-made person-detection model on a laptop with sample photos.
- Week 5: accuracy check against a free dataset at the image size the board will use, compared with true labels.

Both are done on the laptop. Code and results live in `ai/`; this note records the decisions and what
we learned that affects the rest of the plan.

## Decisions

1. **Model: ST's YOLOv8n person detector, 256x256 input, int8.** ST publishes four sizes (192/256/320/416)
   trained on COCO person through their Ultralytics fork, already quantized for the STM32N6's NPU. 256 is
   the default because it fits in the N6's internal RAM (624 KiB) at ~24 ms per frame on the Discovery Kit,
   which leaves headroom for tracking and servo control. 320 is the fallback if accuracy on small/far
   people turns out to matter more than 6 ms. All four were measured so the trade-off is on paper.
2. **Laptop runtime: LiteRT (the TFLite runtime) on CPU, Python 3.12.** No GPU on this laptop, none needed.
   The int8 models run in 7 to 20 ms per image on CPU. Python 3.14 is the default here but has no TFLite
   wheels, so the project venv pins 3.12 and is managed with `uv`. STM32CubeIDE 2.1.1 is already installed;
   ST Edge AI Core is not yet (it is a Week 6 item, needed for the board, not for the laptop work).
3. **Dataset: the full COCO val2017 set, person class only (5,000 images, 10,777 person boxes, 227
   crowd regions).** It is free, it is what ST trained and evaluated on, and using all of it means our AP
   is directly comparable with ST's published number for each model rather than a noisy subset. Images
   without people are included so false positives count. `--n-with-person/--n-without` give fixed-seed
   subsets for quick runs.
4. **Evaluation settings copied from ST's README so the comparison is fair:** a detection is correct at
   IoU >= 0.5, NMS 0.5, score threshold 0.001, max 100 boxes per image, "fit" (stretch) resize, which is
   also what the N6 camera pipeline does in hardware. We wrote our own evaluator (tested, ~150 lines) and
   cross-check it against the official COCO API (`--pycocotools`).
5. **Report the operating point, not just AP.** `metrics.json` has precision / recall / F1 at thresholds
   0.1 to 0.9 and the best-F1 threshold. The int8 models output scores in coarse steps (0.50, 0.64, 0.76,
   0.85, 0.92), so the demo threshold must come from this sweep. 0.5 was too strict: on the 13-person
   sample photo it kept one box.
6. **Repo layout:** one repo, folders per owner (`ai/`, `station/`, `firmware/`, `hardware/`, `Docs/`).
   Models and data are downloaded by script and git-ignored; small result files are committed as evidence.

## Findings that affect the plan

- **Camera on the NUCLEO-N657X0-Q is confirmed compatible.** The board's 22-pin FFC MIPI CSI-2 connector
  takes ST's B-CAMS-IMX module (MB1854B, Sony IMX335), the same module the Discovery Kit ships with, and
  ST says the DK's IMX335 BSP driver can be reused. Raspberry-Pi-style IMX219 cameras need a driver we
  would have to write. (ST community threads; UM3300 table 19 has the pinout.) Order the B-CAMS-IMX.
- **ST's "people detection and tracking" demo only tracks on the Discovery Kit.** The Nucleo build of
  `x-cube-n6-ai-people-detection-tracking` ships TinyYOLOv2 with no tracking or box filtering, and shows
  output over USB UVC (webcam app on the laptop) or an optional SPI display, since the Nucleo has no LCD.
  Week 7's "run ST's tracking demo on the board" therefore becomes: run ST's detection demo on the Nucleo,
  then port or write the tracker ourselves (a simple IoU/centroid tracker is fine for one camera).
- **Pin one ST Edge AI Core version for the team.** Current release is 4.0.0 (the model zoo numbers use
  it); the application packages were built with 3.0.0 and ST warns a mismatch gives a
  "Possible mismatch in ll_aton library" build error. Install into a path without spaces.
- **Deploy through the model zoo services, not by hand-swapping files.** Several people report a black
  screen or missing boxes after dropping YOLOv8n into the N6 demo app manually; ST's answer is to run the
  model zoo `deployment` mode, which generates the app config for the chosen model. The main model zoo
  repo needs Git LFS; we download the individual model files instead.
- **Critical assumption 1 (person re-identification across cameras): ST does ship a candidate model.**
  Model zoo v4.0 added a Re-Identification use case with OSNet and MobileNetV2 variants
  (`stm32ai-modelzoo/re_identification/`). OSNet 0.25, int8, 256x128 input: 3.5 ms and 480 KiB RAM on the
  N6570-DK; OSNet 1.0: 13.4 ms, 1440 KiB. Caveats for Week 6: it is trained on DeepSportradar (basketball
  players: 486 identities, mAP 70-74 %, rank-1 90-92 % on that set), so accuracy on ordinary clothing in a
  retail/office scene is unverified. We downloaded both files and checked the tensors: input
  (1, 256, 128, 3) uint8, output (1, 128) int8 for 0.25 and (1, 512) int8 for 1.0, i.e. an embedding
  vector, not class scores, so the matching recipe is dequantize, L2-normalize, cosine distance. Fallback
  for the Winter demo remains a geometric handoff (position + timing). `scripts/download_models.py`
  fetches both OSNet files.

## Results

Full-set numbers are in `ai/results/summary.md` and per-model `ai/results/<model>/metrics.json`.
The Week 4 annotated sample photos are in `ai/results/week4_samples/`.

**Week 5 accuracy and speed, COCO val2017, 5,000 images, 10,777 person boxes (laptop, 2026-11-02):**

| model | AP@0.5 ours | AP@0.5 COCO API | AP@0.5 ST published | P / R at thr 0.25 | P / R at thr 0.5 | laptop CPU invoke, median | ST time on N6570-DK |
|---|---|---|---|---|---|---|---|
| yolov8n 192 | 0.507 | 0.500 | 0.536 | 0.87 / 0.37 | 0.93 / 0.30 | 4.0 ms | 16.3 ms |
| **yolov8n 256** | **0.577** | **0.570** | **0.584** | **0.88 / 0.42** | **0.97 / 0.27** | **6.9 ms** | **23.8 ms** |
| yolov8n 320 | 0.623 | 0.616 | 0.619 | 0.86 / 0.48 | 0.92 / 0.41 | 10.9 ms | 29.9 ms |
| yolov8n 416 | 0.667 | 0.660 | 0.648 | 0.88 / 0.53 | 0.93 / 0.41 | 24.9 ms | 54.7 ms |

What this says:

- Our measurement reproduces ST's published AP within 3 points for every size (slightly below at 192/256,
  slightly above at 320/416; the remaining gap is resize kernels and CPU vs NPU int8 arithmetic). Our
  evaluator agrees with the official COCO API within 0.007 on all four, so the numbers can be trusted.
- Accuracy rises steadily with input size, and so does cost: 320 buys +4.6 AP over 256 for +6 ms on the
  board; 416 buys another +4.4 for +25 ms and 2 MB of RAM, which no longer fits internal SRAM.
  **Decision stands: 256 by default, 320 if far-away people matter in the demo space.**
- Recall on COCO looks low (0.42 at our threshold) because COCO labels every tiny background person;
  precision is what matters for a lingering alarm, and it is 0.88 at threshold 0.25 and 0.97 at 0.5.
- The int8 scores are quantized to seven levels, so only thresholds 0.1 / 0.2 / 0.25 / 0.5 / 0.7 / 0.8 /
  0.9 are distinct. We set the operating threshold to 0.25 (scores >= 0.36).

**Week 4 run (yolov8n 256, threshold 0.25, `ai/results/week4_samples/`):** 7 photos, 12 boxes,
7.9 ms mean invoke on the laptop CPU. One standing person: found at 0.91. Two and three people: all
found. Five people and the 13-person crowd: 2 found each, which is the small-person recall limit of a
256-pixel input and the reason to re-test with 320 once the demo distance is known. No-person photo:
no boxes.
